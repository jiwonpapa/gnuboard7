# 쇼핑몰 상품 목록·상세 병목 상세 분석

## 1. 결론

현재 성능 저하는 한 가지 원인이 아니라 다음 병목이 연쇄적으로 증폭되는 구조입니다.

1. 목록·상세 화면이 진입 즉시 API 5개를 각각 병렬 호출합니다.
2. PHP-FPM은 최대 6개 요청만 처리할 수 있어 10 VU에서 최대 50개 API가 6개 워커 앞에 대기합니다.
3. 워커가 실행하는 API 자체도 목록 74 SQL, 분류 182 SQL, 인기상품 49 SQL로 무겁습니다.
4. 상품 목록 직렬화 과정에서 썸네일·카테고리 경로·권한 N+1이 발생합니다.
5. 목록은 매 요청마다 전체 COUNT를 수행하고 깊은 페이지에서는 OFFSET만큼 읽고 버립니다.
6. 인기상품은 전체 공개 상품에 30일 판매량 상관 서브쿼리를 계산하고 임시 테이블을 정렬합니다.

현재 10,000건에서도 실제 목록 화면 p95가 5.81초, 상세 화면 p95가 3.46초입니다. 리뷰·주문·문의·쿠폰 데이터가 0건인 최선 조건이므로, 현재 구조를 그대로 운영 쇼핑몰에 적용하기는 어렵습니다.

## 6. 병목 상세

### P0. 상품 목록 직렬화 N+1

목록 12개 응답의 74 SQL 중 반복 쿼리는 다음과 같습니다.

| 반복 쿼리 | 횟수 | DB 시간 | 발생 원인 |
|---|---:|---:|---|
| 상품 권한 존재 확인 | 27 | 9.82ms | 상품별 수정·삭제 2회 + 컬렉션 권한 3회 |
| 카테고리 조상 조회 | 24 | 8.87ms | 상품별 breadcrumb를 두 번 계산 |
| 대표 이미지 조회 | 12 | 5.84ms | eager-loaded `images`를 쓰지 않고 관계를 재조회 |

#### 대표 이미지

- Repository는 이미 `images`를 eager-load합니다: `ProductRepository.php:380-383`.
- Resource는 상품마다 `getThumbnailUrl()`을 호출합니다: `ProductListResource.php:24-31`.
- `getThumbnailUrl()`은 로드된 컬렉션 대신 `$this->images()` 쿼리를 새로 실행합니다: `Product.php:183-187`.

#### 카테고리 경로

- Resource는 같은 카테고리에서 `getBreadcrumb()`를 두 번 호출합니다: `ProductListResource.php:67-70`.
- `getBreadcrumb()`는 매번 path의 조상 ID를 다시 조회합니다: `Category.php:184-205`.

#### 권한

- 상품마다 `resourceMeta()`가 수정·삭제 권한을 확인합니다: `ProductListResource.php:114-129`.
- 권한 확인은 DB `exists()`를 실행합니다: `User.php:242-251`, `AuthServiceProvider.php:48-59`.
- guest 역할은 permissions를 eager-load하지만 실제 guest 확인은 다시 관계 쿼리를 실행합니다: `AuthServiceProvider.php:231-252`.

이 병목은 상품 수가 아니라 페이지당 반환 건수에 비례합니다. `per_page=12`에서도 63개의 불필요한 반복 SQL이 발생합니다.

### P0. 분류 트리 재귀 N+1과 반복 COUNT

분류 API 한 번에 182 SQL이 실행됩니다.

| 쿼리 유형 | 횟수 | DB 시간 |
|---|---:|---:|
| 자식 분류 + 상품수 상관 COUNT | 101 | 83.2ms |
| 분류 이미지 | 41 | 14.3ms |
| 부모 분류 | 40 | 10.4ms |

`Category::getTree()`는 각 노드마다 자식 조회를 재귀 호출하고, 매 단계에서 이미지·부모·상품수를 다시 조회합니다: `Category.php:309-328`. 공개 API는 이 메서드를 매 요청마다 캐시 없이 호출합니다: `CategoryService.php:62-72`.

`EXPLAIN ANALYZE`에서 한 분류의 상품수 집계만 피벗 657행과 상품 PK 1,314회를 조회해 약 2.28ms가 걸렸습니다. 이 패턴이 전체 트리에서 반복됩니다.

### P0. 인기상품 전체 스캔·상관 집계·정렬

인기상품 SQL 한 개가 유휴 상태에서도 146~156ms를 사용합니다.

- 전체 공개 상품 9,494행을 조회합니다.
- 각 상품마다 최근 30일 `order_options.quantity` 합계를 계산합니다.
- 결과 9,494행을 임시 테이블에 저장합니다.
- 계산된 `recent_sold`로 전체 정렬한 뒤 8개만 반환합니다.

근거 코드는 `ProductRepository.php:446-461`입니다. 현재 주문옵션이 0건인데도 전체 상품별 상관 서브쿼리와 정렬 비용이 발생합니다. 실제 주문 데이터가 쌓이면 더 악화됩니다. `order_options`에는 `product_id` 단일 인덱스만 있고 `(product_id, created_at)` 복합 인덱스도 없습니다.

### P0. 목록 COUNT·인덱스·OFFSET

목록은 `paginate()`를 사용해 매 요청마다 전체 COUNT와 OFFSET 조회를 실행합니다: `ProductRepository.php:378-440`.

#### COUNT

```text
Index lookup display_status='visible': 9,494 rows
deleted_at filter: 9,494 rows
actual: 21.5ms
```

`display_status`와 `created_at`은 각각 단일 인덱스지만, 실제 조건과 정렬을 함께 만족하는 `(display_status, deleted_at, created_at, id)` 복합 인덱스가 없습니다: `2026_04_01_000005_create_ecommerce_products_table.php:51-58`.

#### OFFSET

| 페이지 | OFFSET | 읽고 정렬한 행 | 목록 본쿼리 |
|---:|---:|---:|---:|
| 1 | 0 | 12 | 약 0.1~1ms |
| 396 | 4,740 | 9,494 중 4,752 | 50.7~51.2ms |
| 792 | 9,492 | 9,494 | 66.4~66.6ms |

현재 UI는 이전·다음만 제공하지만 API는 임의의 `page`를 받고 전체 페이지 수도 반환합니다: `_product_grid.json:83-163`. 데이터가 늘면 깊은 페이지 비용이 OFFSET에 비례해 증가합니다.

### P1. 화면 API 팬아웃

각 요청이 가벼워도 사용자 10명이 목록에 진입하면 50개 PHP 요청이 생성됩니다. 현재는 분류·인기상품처럼 무거운 요청이 6개 워커를 오래 점유해 신상품·최근상품·목록까지 대기시킵니다.

화면별 p95가 단독 API보다 크게 증가한 이유는 다음 순서입니다.

```text
5 API auto_fetch
  -> PHP-FPM 6개 워커 포화
  -> 대기 요청 증가
  -> CPU 93~100%
  -> 실행 중 요청도 느려짐
  -> 워커 반환 지연
  -> 대기열 추가 증가
```

### P1. 응답 과적재

상품 12개 목록 응답이 약 30KiB입니다. 목록에서 모든 이미지·카테고리·브랜드·라벨·리뷰 통계·권한·다중통화 필드를 구성합니다. 특히 목록은 대표 이미지만 필요하지만 `images` 전체를 eager-load합니다: `ProductRepository.php:380-383`.

이미지가 상품당 여러 장, 라벨·카테고리가 다수로 늘면 SQL 개수뿐 아니라 Eloquent 모델 생성, JSON 변환, 네트워크 크기도 함께 증가합니다.

### P2. 현재 데이터에서는 드러나지 않은 확장 병목

#### 상품 문의

문의는 DB 페이지네이션 전에 해당 상품의 피벗과 게시글을 모두 읽고 PHP에서 `forPage()` 처리합니다: `ProductInquiryService.php:84-116`. 문의가 많아지면 페이지와 무관하게 전체 문의를 매번 메모리에 올립니다.

#### 다운로드 쿠폰

모든 다운로드 가능 쿠폰을 가져온 뒤 PHP에서 상품 적용 여부를 필터링합니다: `UserCouponService.php:441-451`. 로그인 사용자는 필터된 쿠폰마다 발급 여부를 개별 조회합니다: `UserCouponService.php:454-479`.

#### 리뷰

리뷰 화면은 목록 `paginate()` 외에 별점 분포, 옵션 목록, 옵션별 리뷰 수를 별도 집계합니다: `ProductReviewRepository.php:122-188`. 현재 리뷰가 0건이라 빠르지만 리뷰가 쌓이면 복합 인덱스와 집계 캐시가 필요합니다.

## 7. 개선 우선순위

### 1단계: 쿼리 폭발 제거

1. `getThumbnailUrl()`이 `images` relationLoaded 상태면 메모리 컬렉션을 사용합니다.
2. 상품별 breadcrumb는 요청 단위로 한 번만 계산하고, 전체 조상 분류를 일괄 로드합니다.
3. guest·회원 권한은 요청 단위로 캐시하고 상품 목록의 동일 권한은 컬렉션 레벨에서 한 번만 판정합니다.
4. 분류 트리는 평면 1회 조회 + 일괄 상품수 집계 + PHP 트리 구성으로 바꾸고 짧은 TTL로 캐시합니다.

목표는 목록 12개 `74 SQL -> 10개 이하`, 분류 `182 SQL -> 5개 이하`입니다.

### 2단계: 핵심 SQL 구조 변경

1. 상품에 `(display_status, deleted_at, created_at, id)` 복합 인덱스를 추가합니다.
2. 정렬을 `created_at DESC, id DESC`로 고정해 동률에서도 결정적 순서를 보장합니다.
3. 깊은 페이지는 cursor pagination으로 전환하고 전체 건수는 별도 캐시·집계값으로 제공합니다.
4. 인기상품은 요청 시 상관 서브쿼리를 제거하고 일별 판매 집계 테이블 또는 캐시된 Top-N을 사용합니다.
5. 주문 기간 집계가 필요한 경로에는 데이터 분포에 맞춰 `(product_id, created_at)` 또는 `(created_at, product_id)` 인덱스를 검증 후 적용합니다.

### 3단계: 화면 요청 구조 변경

1. 목록 핵심 데이터는 상품 목록 1개를 우선 렌더링합니다.
2. 분류·인기·신상품은 서버 캐시된 bootstrap 응답으로 묶거나 지연 로드합니다.
3. 상세의 리뷰·문의·쿠폰은 해당 탭을 열 때 로드합니다.
4. 인기상품은 목록과 상세에서 공통 캐시를 사용합니다.

PHP-FPM `max_children` 증가는 이 작업 뒤에 메모리와 CPU를 측정해 결정해야 합니다. 현재 2 vCPU에서 워커만 늘리는 것은 근본 해결이 아닙니다.

## 8. 개선 후 수용 기준

동일 서버·동일 데이터·10 VU 조건에서 다음을 확인해야 합니다.

| 지표 | 목표 |
|---|---:|
| 상품 목록 단일 API p95 | 200ms 이하 |
| 분류 단일 API p95 | 200ms 이하 |
| 인기상품 단일 API p95 | 200ms 이하 |
| 실제 목록 화면 p95 | 800ms 이하 |
| 실제 상세 화면 p95 | 800ms 이하 |
| CPU 평균 | 70% 이하 |
| HTTP 오류율 | 1% 미만 |
| FPM max_children 경고 | 0건 |

그다음 상품 50,000건, 100,000건과 리뷰·주문 데이터가 포함된 단계별 데이터셋으로 같은 테스트를 반복해야 합니다.

상품 20,000건 중 공개 18,988건을 고정하고 공식 7.0.4 원본과 개선 패치를 각각 10 VU, 30초로 측정했습니다.

| 화면 | 원본 평균 / p95 | 개선 평균 / p95 | 원본 CPU busy | 개선 CPU busy | 화면 처리량 증가 |
|---|---:|---:|---:|---:|---:|
| 목록 | 5.38s / 7.61s | 327ms / 861ms | 99.96% | 78.87% | 5.5배 |
| 상세 | 2.12s / 3.99s | 249ms / 644ms | 89.28% | 76.31% | 3.4배 |

패치는 쿼리 N+1 제거, 짧은 캐시, 인기상품 집계 변경, 복합 인덱스, 목록 API 통합, 상세 탭 지연 로드를 적용했습니다. 오류율은 모두 0%였고 상세 p95 800ms 목표는 충족했습니다. 목록 p95는 861ms, CPU는 76~79%로 목표에 소폭 미달했습니다.

현재 병목 우선순위는 다음과 같습니다.

1. 2 vCPU에서 PHP-FPM 직렬화와 MySQL이 동시에 CPU를 소비합니다.
2. 목록 COUNT·OFFSET은 그대로라 상품 수 증가 시 다시 악화됩니다.
3. 캐시 만료 직후 분류·인기상품 재계산 비용이 남아 있습니다.
4. 운영 규모에서는 인기상품 집계 테이블과 cursor pagination이 추가로 필요합니다.

패치는 `scripts/benchmark/ecommerce-performance-toggle.sh`로 공식 원본과 반복 전환할 수 있습니다. 상세 파일과 인덱스 목록은 `docs/benchmark/ecommerce-performance-toggle-harness.md`에 기록했습니다.

초기 A/B는 하네스가 production 캐시를 재생성하지 않아 절대 수치를 폐기했습니다. 위 결과는 config/routes/views/hooks 캐시를 복구한 뒤 2만 건으로 전 구간을 다시 측정한 최종 수치입니다.
