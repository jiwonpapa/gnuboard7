# 그누보드7 7.0.5 성능 튜닝 코드 지도·설계 근거·재현 프롬프트

- 작성일: 2026-07-21 KST
- 공식 기준선: 태그 `7.0.5`, 커밋 `d5065f1bc9ebdc31a3e4e0d0c2e757138fd7423f`
- 검토한 튜닝 소스: 커밋 `3379ed93`
- 결과 보고서가 추가된 저장소 상태: 커밋 `0237e21b`

- 시험 서버: 4 vCPU·8GB·2GB swap, Ubuntu 24.04, MySQL 8.4, PHP-FPM 8.5, Redis, Manticore
- 상태: 코드 지도와 구현 계약 문서. 단순 성능 결과는 [VM 성능 보고서](g7-7.0.5-vm-performance-report-2026-07-21.md)를 참조한다.

## 1. 결론

기존 문서는 게시판, 쇼핑몰, 검색, 하네스, VM 실측으로 나뉘어 있어 전체 튜닝을 한 번에 추적하기 어려웠다. 이 문서는 그 조각을 하나의 변경 추적표로 합친 것이다.

핵심 튜닝은 다음 다섯 축이다.

1. 공통 요청 비용: 훅 등록 로그, 비회원 권한, 활성 모듈, 언어팩 조회의 반복 비용을 줄였다.
2. 게시판: 목록에서 큰 행을 먼저 읽거나 잘못된 인덱스를 타는 문제, 중복 count, 공지·답글 무제한 확장, 광범위 검색의 메모리 폭증을 제한했다.
3. 쇼핑몰: 상품 전체 행에 관계를 붙인 뒤 페이지를 자르던 구조, 카테고리 N+1, 인기상품 상관 서브쿼리, 리소스의 반복 계산을 줄였다.
4. 통합검색: MySQL FULLTEXT의 정확도·메모리 양립 실패 구간을 Manticore 읽기 경로로 분리했다.
5. 검증·원복: 공식 7.0.5와 튜닝 상태를 같은 VM·DB·요청으로 전환하고, 자원과 응답 의미를 함께 판정하는 하네스를 만들었다.

이 문서의 라인 번호는 `3379ed93`의 소스 기준이다. 이후 편집으로 줄 번호가 달라질 수 있으므로 **파일 경로와 심볼 이름이 정본이고, 줄 번호는 탐색용 앵커**다.

## 7. 코드 불변조건

아래 조건이 깨지면 평균 지연시간이 좋아져도 튜닝 성공으로 보지 않는다.

1. 권한 결과, 공개 상태, 삭제 상태, 게시판 범위가 기준선과 같아야 한다.
2. 검색 결과가 잘렸으면 `total_relation=gte`, `total_is_exact=false`, `search_truncated=true`를 숨기지 않아야 한다.
3. Manticore가 정확 결과를 반환하면 `total_relation=eq`이고 MySQL hydration 순서는 Manticore ID 순서를 보존해야 한다.
4. Manticore 장애 fallback이 원래의 무제한 MySQL FULLTEXT를 다시 실행하면 안 된다.
5. 검색 429는 일반 500으로 변환하지 않아야 한다.
6. 게시판 전용 인덱스 강제는 기본 board·비검색·ID sort에만 적용해야 한다.
7. 상품 `sales` 정렬은 현재 ID-first 최적화 대상이 아니므로 기존 의미를 유지해야 한다.
8. resource cache는 요청 문맥을 넘어서 사용자·통화·locale 결과를 공유하면 안 된다.
9. category static lookup은 필요한 조상을 먼저 prime하고 long-lived worker에서 요청 간 잘못된 상태가 남지 않아야 한다.
10. OFF/ON 비교는 같은 서버·DB·경로·부하에서 해야 하며 phase 사이 앱 캐시를 재생성해야 한다.
11. 전환 실패 후 source/runtime/schema가 섞인 상태를 성공으로 보고하면 안 된다.
12. `restore`는 사전 스냅샷이 완전할 때만 실행하고, 실패하면 비교 산출물을 유효 결과로 남기면 안 된다.

## 11. ROI 기준 다음 작업 순서

1. 게시판 직접검색을 Manticore에 연결하고 정확 total과 현재 페이지 ID만 MySQL에서 hydrate한다.
2. 게시글·상품·페이지 쓰기 이벤트와 Manticore RT/delta 동기화를 구현한다.
3. Manticore 장애 시 DB로 부하가 전이되지 않도록 회로차단기와 backend별 fallback budget을 둔다.
4. ecommerce 인덱스를 benchmark 모듈에서 정식 ecommerce upgrade step으로 옮긴다.
5. 대량 삭제와 table rebuild를 별도 비동기 유지보수 작업으로 분리한다.
6. 위 항목 뒤에 인기상품 집계와 cursor pagination을 측정 기반으로 검토한다.

Rust 전면 재작성은 이 순서에 포함하지 않는다. 현재 확인된 큰 효과는 잘못된 인덱스 선택, 무제한 FULLTEXT, 중복 count, 넓은 row hydration, N+1을 고쳐 얻었다. 언어를 바꾸기 전에 데이터 접근 알고리즘과 운영 경계를 고치는 ROI가 훨씬 높다.

구현 불변조건
- 일반 게시판 목록은 검색 throttle 대상이 아니다.
- 실제 search 요청만 10회/분과 named lock 보호를 받는다.
- 429를 500으로 바꾸지 않는다.
- 게시판 기본 ID 정렬에만 idx_board_posts_list_id를 강제한다.
- 공지는 첫 페이지 최대 10건, 인라인 답글은 페이지 전체 최대 100건이다.
- 제한형 검색은 total_relation=gte, total_is_exact=false, search_truncated=true를 표시한다.
- 정확 검색은 total_relation=eq를 표시한다.
- Manticore 결과는 현재 페이지 ID만 MySQL에서 hydrate하고 검색 순서를 보존한다.
- Manticore 연결을 mysql로 전환해도 서비스와 인덱스를 제거하지 않는다.
- 상품 sales 정렬은 검증 없이 ID-first로 바꾸지 않는다.
- CacheInterface/StorageInterface 같은 프로젝트 추상화를 우회하지 않는다.
- Listener에서 Model/DB를 직접 조작하지 않는다.
- 공개 API나 확장 표면 변경 시 module.json/composer.json 의 g7_version/dependencies와 CHANGELOG를 함께 검토한다.

DB 검증
- SHOW INDEX와 information_schema로 이름만이 아니라 컬럼 순서, uniqueness, visibility를 확인한다.
- EXPLAIN ANALYZE는 기본 게시판 created_at/id sort, 이전·다음, 상품 latest/price/sales, 상품 검색에 수행한다.
- 5초 이상 query/transaction이 있으면 전환을 중단한다.
- innodb_ft_result_cache_limit은 optimized에서 32MiB인지 확인한다.
- restore에서는 캡처한 원래 값으로만 되돌리고 임의 기본값을 쓰지 않는다.
- 대량 삭제 후 파일 크기와 논리 행 수를 구분한다. OPTIMIZE/TABLE rebuild를 웹 요청 안에서 실행하지 않는다.

VM A/B 절차
1. git status와 서버 strict status를 저장한다.
2. DB 행 수, 인덱스 shape, 서비스 상태, 메모리, swap, 장기 query를 preflight한다.
3. g7-ab-benchmark.sh --repeats 3을 실행한다.
4. baseline/optimized 모두 HTTP, semantic, dropped iteration, sampler heartbeat를 검증한다.
5. g7-search-ab-benchmark.sh --repeats 3을 실행한다.
6. baseline+mysql, optimized+mysql, optimized+manticore를 순서대로 비교한다.
7. 마지막 상태가 optimized+Manticore인지 strict status와 실제 API로 확인한다.
8. 실패 또는 중단 시 원래 정상 상태로 복구되기 전까지 결과를 PASS로 보고하지 않는다.

자원 안전장치
- available memory가 400MiB 미만으로 3회 연속 내려가면 phase 중단
- swap이 시작 대비 64MiB 이상 증가하면 중단
- HTTP/semantic error 또는 iteration drop이면 해당 phase 무효
- sampler heartbeat가 끊기면 CPU/RSS 비교 무효
- 위험 검색은 일반 부하에 섞지 말고 기본 한 요청 또는 별도 phase로 실행

성공 기준
- CODE_ONLY: 소스·마이그레이션·설정·테스트가 존재하고 정적 검토 PASS
- AUTO_PASS: 관련 PHP/shell 테스트와 응답 의미 검증 PASS
- VPS_PASS: 실제 VM 전환, health, EXPLAIN, HTTP, CPU/RSS/memory/swap, 복구까지 PASS
- 하나의 수준을 다른 수준으로 과장하지 않는다.
- 각 변경을 파일:현재라인, 심볼, 기존 병목, 새 알고리즘, 불변조건,
  설정/토글, 테스트, 실측, rollback, 남은 위험 순서로 보고한다.
- 개선되지 않은 지표와 불완전 검색도 숨기지 않는다.

금지
- 전체 diff를 모두 런타임 튜닝으로 계산하지 않는다.
- 서로 다른 서버/데이터/부하의 숫자를 A/B로 비교하지 않는다.
- p95가 좋아졌다는 이유만으로 오류 응답이나 잘린 결과를 성공으로 계산하지 않는다.
- MySQL error 188 외의 DB 오류를 무조건 fallback으로 숨기지 않는다.
- Manticore가 빠르다는 이유로 실시간 인덱스 동기화 완료를 주장하지 않는다.
- 공식 문서에 없는 CPU/RAM 수치를 공식 최소사양이라고 쓰지 않는다.
- 사용자 미커밋 파일을 수정, 삭제, stage하지 않는다.

## 14. 해석 제한

- 숫자는 4 vCPU·8GB VM의 낮은 고정 부하 3회 반복 결과다. 최대 TPS 자료가 아니다.
- 일반 경로 결과와 검색 결과는 별도 하네스이므로 같은 행의 단일 부하시험처럼 합산하면 안 된다.
- 서버 사양은 공식 최소사양이 아니라 현재 데이터 규모에서 관찰한 하한·권장치다.
- Manticore 검색 성능은 검증됐지만 실시간 색인 freshness는 아직 검증 완료가 아니다.
- `3379ed93` 이후 소스가 바뀌면 먼저 심볼을 찾고 줄 번호와 쿼리 계획을 다시 산출해야 한다.
