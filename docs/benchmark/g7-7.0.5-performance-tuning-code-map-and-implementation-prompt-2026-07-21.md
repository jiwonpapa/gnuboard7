## 0. 빠른 판정

**개발자 인수 판정은 `구현 착수 가능`이다.** 이 문서만으로 병목별 파일·심볼, 기존/변경 알고리즘, 인덱스 목적, 테스트, A/B 절차, 불변조건, 원복과 ROI 우선순위를 찾을 수 있다. 다만 독립 재현·감사까지 하려면 저장소 checkout, 전용 `.env.testing`·test DB, R/G/X 스냅샷 또는 동등한 데이터, 6.6의 원시 산출물 묶음을 함께 전달해야 한다.

**호스팅 판정은 `VPS 가능, 공유호스팅은 통합검색 제외 조건부`다.** 현재 검증 규모의 권장은 4 vCPU·8GB이며, 카페24 뉴아우토반 절약형은 통합검색을 끈 기본 설치·극저트래픽만 조건부 가능하고 정상 쇼핑몰 운영용으로는 권장하지 않는다. PHP `memory_limit` 256M/512M은 MySQL FULLTEXT 메모리를 제한하지 않는다.

## 1. 결론

같은 4 vCPU·8GB VM에서 현실 기준 R과 성장 기준 G를 각각 같은 스냅샷·15 RPS·5분으로 비교했다. R은 전체 p95가 **107.900→64.966ms(-39.79%)**, 호스트 CPU가 **19.767→13.031%(-34.08%)**, MySQL CPU가 **5.242→1.364%(-73.98%)**였다. G는 p95가 **225.161→49.947ms(-77.82%)**, 호스트 CPU가 **27.465→12.775%(-53.49%)**, MySQL CPU가 **12.643→1.695%(-86.59%)**였다. 네 phase 모두 HTTP·의미 오류·drop·swap이 0이었다. 다만 5분 gate이므로 30분 steady나 2시간 soak 인증으로 확대 해석하지 않는다.

X 저부하 경로 분석에서는 가장 큰 단일 병목이 게시판 ID 정렬의 잘못된 인덱스 선택으로 확인됐고, API 중앙값이 **759.866ms에서 52.413ms(-93.10%)**로 줄었다. 쇼핑몰은 카테고리 N+1과 전체 행 hydration을 제거해 주요 경로가 **46.70~72.52%** 개선됐다. 이 수치는 R/G 운영부하 결과와 별도 증거다.

검색은 애플리케이션 미세 튜닝만으로 해결되지 않는다. 현재 네이티브 통합검색은 한 요청에서 모듈별 MySQL FULLTEXT 검색과 exact count를 합산하는 구조라 광범위 검색의 메모리·동시성 비용을 코어가 통제하기 어렵다. 실제 count 한 번이 mysqld RSS를 약 **903MB** 늘렸고, 메모리 상한을 안전하게 낮추면 error 188 또는 제한형 하한 결과가 발생했다. 이는 **현재 그누보드7 네이티브 MySQL 통합검색이 대량·광범위 검색에서 정확도와 서버 생존성을 함께 보장하기 심각하게 어렵다**는 증거다. Manticore는 도입 권고가 아니라 외부 검색엔진이 이 병목의 대안이 될 수 있는지 확인한 시험 사례다.

| 현재 네이티브 통합검색 흐름 | 구조적 한계 |
|---|---|
| `PublicSearchController.php:39-57`이 `core.search.results` 훅으로 모든 활성 검색 모듈을 순차 호출 | 코어가 backend별 실행시간·메모리 budget·capability·장애 정책을 통합 제어하지 못함 |
| `SearchPostsListener.php:85-123`, `SearchProductsListener.php:87-131`, `SearchPagesListener.php:79-113`이 각자 search 또는 count 실행 | 한 HTTP 요청이 게시글·상품·페이지의 독립 DB 검색/count를 연쇄 실행하고 모듈이 늘수록 비용이 누적 |
| `PublicSearchController.php:89-125`가 모듈 total을 합산 | exact 전체 건수를 유지하려면 광범위 후보 count를 피하기 어렵고, 한 모듈 실패·누락이 빠른 정상 응답처럼 보일 위험 |
| G7은 이미 `ScoutServiceProvider.php:33-51`에서 `core.search.engine_drivers`와 `EngineManager::extend()`를 제공 | 별도 외부 검색 driver/registry는 불필요. 다만 Scout를 쓰지 않는 Repository는 등록만으로 자동 전환되지 않으며, 이번 Manticore 직결 코드는 읽기 성능 비교용 |

### 1.2 배포 판단

- **현재 대용량 시험 데이터의 권장 사양은 4 vCPU·8GB**다. 일반부하·검색·색인을 분리된 phase로 실행했을 때 모두 swap 0과 충분한 가용 메모리를 유지했기 때문이다. 세 작업을 동시에 겹친 검증은 아직 아니다.
- **4 vCPU·4GB는 저부하 smoke 하한 후보**다. 21개 경로를 0.2 RPS·20초·1회 통과했을 뿐 검색·색인·큐 중첩과 steady는 검증하지 않았다.
- **2GB는 부적합**하다. 가용 메모리 379MB에서 안전장치가 3초 만에 시험을 중단했고, MySQL FULLTEXT 한 번의 RSS 증가량만 약 903MB였다.
- **카페24 뉴아우토반 500원형은 통합검색을 비활성화한 초저트래픽·동기 처리·기능 축소 상태에서만 조건부 구동 후보이며 정상 운영 권장 대상은 아니다.** 700MB 디스크가 G7 공식 최소치와 같아 업데이트·캐시·로그·첨부파일 여유가 없고, 공유 CPU/RAM도 보장되지 않는다. PHP `memory_limit` 256M/512M은 MySQL FULLTEXT 메모리 문제의 해결책이 아니다. 상세 판정은 7장에 정리했다.

### 1.3 게시글 70만 건에서 MySQL FULLTEXT가 메모리를 소진한 이유

문제는 “70만 건이 절대적으로 거대한가”보다 **검색어가 678,866건, 전체 게시글의 96.98%에 매칭됐다는 점**이다. MySQL 공식 문서상 `innodb_ft_result_cache_limit`은 FULLTEXT 쿼리의 중간·최종 결과를 메모리에서 처리하는 **쿼리 또는 스레드별 상한**이다. 기본값은 2GB이며 큰 결과에서 과도한 메모리 사용을 막기 위한 변수다. 따라서 거의 모든 문서가 매칭되는 exact count·relevance 정렬이 겹치면 페이지에서 20건만 보여도 내부 후보는 20건으로 끝나지 않는다. [MySQL 8.4 `innodb_ft_result_cache_limit`](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_ft_result_cache_limit)

이번 사고에서 상품 20,000건은 주원인이 아니었다. 게시글 FULLTEXT의 678,866건 매칭과 exact count가 지배적이었다. 동시 검색이 들어오면 쿼리·스레드별 작업 메모리가 중첩될 수 있으므로 2GB 서버에서는 한 요청도 위험하고 여러 요청은 더 위험하다.

| 대응 | 해결하는 것 | 해결하지 못하는 것 |
|---|---|---|
| ID-first·현재 페이지 hydration | PHP 모델 수, DB 전송량, 관계 N+1 | FULLTEXT exact count가 모든 매칭 후보를 처리하는 비용 |
| 32MiB FULLTEXT cap | OOM·swap으로 서버 전체가 멈추는 사고 | 상한 초과 시 error 188 또는 제한형 하한 결과가 되는 정확도 손실 |
| throttle·named lock | 여러 위험 검색의 메모리 중첩 | 단일 광범위 검색의 근본 비용과 처리량 저하 |
| bounded fallback | 외부 backend 장애가 무제한 MySQL 검색 사고로 번지는 것 | exact total·전체 과거 결과 |
| Manticore 대안 시험 | 통합검색의 광범위 count·정렬을 DB에서 격리하고 MySQL 메모리 폭증 방지 | Scout custom engine 제품화, 실시간 색인 동기화, 권한·삭제 상태 검증, 장애 전환은 이번 성능 수치의 검증 범위가 아님 |

즉 **애플리케이션 튜닝만으로 현재 네이티브 MySQL 광범위 exact FULLTEXT를 싸게 만들 수는 없다.** 이번 Manticore 연결은 DB와 검색 읽기를 분리했을 때 정확 결과와 서버 생존성을 회복할 수 있는지 확인한 대안 실험이며, 그 자체가 G7의 권장 검색 제품이라는 뜻은 아니다. G7은 이미 Laravel Scout 커스텀 엔진 등록 경로를 제공하므로 별도 외부 검색 driver/registry 신설 제안은 필요 없다. 실제 제품 연동은 기존 Scout `Engine`과 `EngineManager::extend()`를 사용하되, 현재 Scout를 우회하는 Repository 검색을 Scout 진입점에 연결하는 작업은 별도다. 이번 수치는 같은 Manticore 색인·쿼리의 읽기 결과에는 유효하지만 Scout adapter 오버헤드·모델 observer/queue 기반 색인 동기화까지 검증한 수치는 아니다. 참고로 시험한 searchd는 유휴 RSS 약 55~105MB, 전체 색인 시 최대 RSS 약 313MB와 디스크 약 502MB를 사용했다.

## 2. 범위와 측정 계약

튜닝 범위는 공통 요청 비용, 게시판 목록·검색, 쇼핑 홈·목록·검색, 통합검색, MySQL 인덱스와 Manticore 읽기 연결이다. 아래 코드 지도에 없는 benchmark UI, 시험 VM 구축, 인증서 같은 보조 작업은 성능 개선량에 포함하지 않는다.

일반 A/B는 두 층으로 실행했다. X에서는 공식 `7.0.5`와 튜닝 ref를 같은 VM·DB·21개 경로에서 각각 3회 돌려 개별 병목을 찾았다. R/G에서는 1 iteration=HTTP GET 1회인 정확 arrival-rate 하네스로 15 RPS를 5분씩 비교했다. HTTP/의미 오류와 iteration drop이 없어야 유효하며, host/PHP/MySQL/searchd CPU·RSS, 가용 메모리, swap, sampler heartbeat를 함께 판정했다. 검색 A/B/C는 위험 쿼리를 일반 부하와 분리해 `공식+MySQL → 튜닝+MySQL → 튜닝+Manticore` 순서로 실행했다.

이 수치는 낮은 고정 부하의 병목 비교이지 최대 TPS나 장시간 soak 결과가 아니다. 일반 경로와 검색 경로는 서로 다른 phase라 합산하지 않는다. 서버 사양은 공식 CPU/RAM 요구사항이 아니라 이 데이터와 서비스 조합에서 관측한 하한·권장치다.

### 2.1 중소형 쇼핑몰 2년차용 데이터셋

`게시글 1,000건·상품 500건`은 설치, CRUD, 응답 스키마를 확인하는 smoke 데이터로는 맞지만 성능 데이터로는 부족하다. 작은 데이터에서는 대부분 메모리에 들어가고 MySQL optimizer의 잘못된 인덱스 선택, deep pagination, FULLTEXT 결과 메모리, 카테고리·관계 N+1의 누적 비용이 드러나지 않는다. N+1은 쿼리 수 assertion으로 찾을 수 있어도 실제 I/O·CPU·메모리 한계는 검증할 수 없다.

다음 값은 업계 평균 통계가 아니라 **2년=730일인 중소형 쇼핑몰을 재현하기 위한 명시적 시험 가정**이다. 실제 운영 지표가 생기면 일 주문·게시글·가입자 수로 다시 산정한다.

#### 2.1.1 G 데이터셋 재생성 입력

G는 아래 세 작업을 순서대로 만든 누적 corpus다. 기록된 G DB에서는 작업 ID 11~13이지만 새 DB의 작업·게시판 ID는 달라질 수 있으므로 이름·seed·slug·입력값을 정본으로 삼는다. 먼저 `GET /api/modules/sirsoft-benchmark/admin/generation-jobs/boards`에서 `freebd`, `gallery`, `test40`의 현재 ID를 조회한다.

| 작업 | 입력 |

관리자 UI 또는 Sanctum·모듈 권한이 있는 `POST /api/modules/sirsoft-benchmark/admin/generation-jobs`로 작업을 등록하면 설정된 queue로 즉시 dispatch된다. 정상 worker가 동작 중이면 아래 CLI를 다시 실행하지 않는다. CLI는 worker를 의도적으로 중지한 격리 환경에서만 queue 실행을 대신하며, 입력을 새로 만드는 명령이 아니라 **이미 등록된 작업 ID를 직접 처리**하는 명령이다.

```bash
php artisan benchmark:generate-dummy-data --job=<NEW_JOB_ID>
```

각 작업이 `completed`이고 생성 카운터가 게시판 `회원 100,000·게시글 200,000·댓글 348,700`, 쇼핑 A/B 각각 `상품 10,000`인지 확인한 뒤 DB 총계를 0.2 표와 비교한다. 총계에는 설치 기본 행이 포함돼 생성 카운터보다 회원 1·게시글 5·댓글 14가 많다.

R과 X의 당시 전체 입력 옵션은 현재 작업 DB에 보존돼 있지 않다. **동일 A/B는 위 VM 복구점을 사용**하고, 복구점을 전달할 수 없으면 새 seed·분포·행 수를 문서화한 `R2`/`X2` corpus로 다시 측정하며 기존 R/X 수치와 동일 시험이라고 표시하지 않는다.

현재 `sirsoft-benchmark` 더미 생성기는 회원·게시글·댓글과 상품·분류·브랜드·옵션·이미지까지만 만든다. **주문·주문상품·결제·배송·리뷰·문의는 아직 생성하지 못하므로 위 R/G 주문 목표는 시험 설계값이지 현재 검증 완료 데이터가 아니다.** 기존 `OrderSeeder`는 소량 샘플·전역 주문 삭제·최근 30일·Eloquent 건별 생성 방식이라 이 스냅샷에 사용하지 않았다. 주문 정합성용 1천~5천 건 domain-service corpus와 `ecommerce_order_options`까지 소유하는 대량·재개형 생성기를 분리 구현하기 전까지 주문·매출·재고·마일리지·인기상품 집계는 `UNVERIFIED`다.

행 수만 맞추면 부족하다. 게시판·상품·주문은 최근 2년에 분포시키고, 일부 인기 게시판·상품에 트래픽이 몰리는 `skewed` 분포, 삭제·비공개·공지·답글, 품절·옵션·다중 분류, 회원/비회원 주문을 포함한다. 검색어도 희소(≤0.1%), 보통(1~5%), 광범위(20~50%), 병리적(≥90%) 매칭을 따로 만들어야 한다. 현재 96.98% 매칭 검색은 마지막 범주다.

### 2.2 운영 부하 시험 강도

4 vCPU·8GB 단일 서버의 초기 목표는 고정 VU 숫자보다 arrival rate와 자원 한계로 정의한다. 검색은 일반 트래픽에 섞으면 원인과 정확도 판정이 흐려지므로 별도 phase로 실행한다.

| 단계 | 권장 부하 | 시간 | 목적 |
|---|---:|---:|---|
| smoke | 1~2 RPS | 3분 | 경로·인증·응답 의미 확인 |
| warm-up | 5 RPS | 5분 | OPcache·DB buffer·앱 캐시 안정화 |
| steady | 15 RPS | 30분 | 예상 정상 운영의 p95와 자원 평형 |
| peak | 30 RPS | 15분 | 중소형 사이트 피크 여유 확인 |
| spike | 33 RPS | 5분 | 현재 30% 게시판 비중에서 600회/분 제한을 넘지 않는 최대 정수 RPS |
| soak | 15 RPS | 2시간 이상 | RSS 증가, connection·cache 누수, DB bloat 징후 확인 |
| breakpoint | 15→30→33→비중 조정 후 상향 | 단계당 10분 | SLO·자원 guard·rate-limit 중 처음 깨지는 지점 확인 |

현재 read-only 운영 phase의 비중은 쇼핑 홈·목록·상세 50%, 게시판 목록·상세 30%, 홈 10%, 쓰기 전 준비용 안전 조회 10%다. POST/PUT/PATCH/DELETE와 로그인·장바구니 실쓰기는 포함하지 않는다. 60 RPS에 이 비중을 그대로 적용하면 게시판이 1,080회/분으로 600회/분 제한을 넘으므로, 제한을 몰래 완화하지 않고 게시판 비중을 16.6% 이하로 낮추거나 rate-limit 검증 phase를 분리해야 한다. 검색 phase는 희소·보통·광범위·병리적 검색어를 각각 단건과 제한된 동시성으로 실행하고 `eq/gte` 의미를 함께 검증한다. 주문 생성 같은 파괴적 쓰기는 별도 DB 스냅샷에서 수행한다.

초기 합격선은 일반 API p95 300ms 이하, p99 1초 이하, Manticore 검색 p95 500ms 이하, HTTP·의미 오류 0, 평균 CPU 70% 이하, 85% 이상 지속 없음, 시작 대비 swap 증가 64MiB 미만(운영 목표 0), 가용 메모리 25% 이상, DB connection 70% 이하, 5초 이상 SQL 없음으로 둔다. 이는 G7 공식 SLO가 아니라 이 시험을 위한 운영 목표다. 가장 중요한 결과는 “60 RPS 통과” 같은 단일 숫자가 아니라 **R과 G 데이터에서 어느 단계에 p95·CPU·메모리·DB가 먼저 무너지는지**다.

### 2.3 외부 재현성 경계

같은 VM 스냅샷 안의 OFF/ON은 서버·DB·데이터·부하가 같아 튜닝 효과 비교에는 유효하다. 그러나 이 공개 문서만으로 다른 장비에 **바이트 단위의 동일 환경**을 만드는 데 필요한 아래 값은 아직 고정되지 않았다.

| 미수집 또는 미고정 항목 | 현재 영향 | 다음 시험의 필수 기록 |
|---|---|---|
| 물리 디스크 종류·backing storage·IOPS/latency | qcow2 상태는 확인했지만 다른 호스트의 I/O 차이를 설명할 수 없음 | 디스크 모델/스토리지 종류, `fio` 기준값, VM disk cache·I/O mode |
| Nginx worker/keepalive와 PHP-FPM pool·OPcache 전체값 | PHP 동시성·RSS를 다른 서버에서 정확히 복제할 수 없음 | `nginx -T`, FPM pool, `php -i` 중 성능 관련 비밀 제거본 |
| MySQL buffer pool·connection·I/O·FULLTEXT 전체값 | 8.4와 32MiB cap 외의 메모리·cache 조건을 완전 재현할 수 없음 | `SHOW VARIABLES` 성능 하위집합과 시작 전 buffer/cache 상태 |
| Redis·Manticore·k6 patch 버전과 설정 전문 | 기능 호환은 판단해도 patch별 차이를 배제할 수 없음 | 각 `--version`, 비밀 제거 설정, index schema 해시 |
| CPU 모델·kernel/sysctl·부하발생기 위치와 RTT | 다른 호스트의 CPU·network 차이를 수치에 섞을 수 있음 | `lscpu`, kernel/sysctl 하위집합, k6 실행 위치·대상 RTT |

다음 공개 A/B부터 `environment-manifest.txt`를 원시 결과 폴더에 생성하고 위 값을 비밀 제거 후 6.6 묶음에 포함한다. 현재 수치는 **동일 VM 내부 비교는 `VPS_PASS`, 타 장비의 완전 동일 재현은 제한됨**으로 읽어야 한다.

성능 variant와 benchmark queue 정의는 `config/benchmark.php:3-87`, 전환 스크립트의 환경변수 기록은 `scripts/benchmark/g7-performance-toggle.sh:1033-1035`다. 통합검색 설정은 `config/scout.php:21-46`, Manticore 예시 환경변수는 `.env.example:59-69`다.

`off`는 성능 비교를 위한 **논리 기준선**이다. `restore`는 파일, DB 인덱스, 설정을 사전 스냅샷 상태로 되돌리는 **물리 원복**이다. 둘을 같은 의미로 사용하면 안 된다.

최종 G VM에서 Laravel runtime을 직접 조회한 값은 `optimized optimized optimized manticore`이고, 순서대로 공통·게시판·쇼핑몰·통합검색이다. benchmark 모듈은 v0.3.2, queue는 `redis/default`, 적재량은 0인 상태로 `g7-g-2y-v032-release-20260721` 스냅샷을 만들었다.

단, 현재 성능 toggle manifest의 benchmark는 v0.2.6이고 최종 운영본은 v0.3.2이므로 `g7-performance-toggle status --strict`는 source drift로 **FAIL**하는 것이 맞다. 최종 VM은 기능상 optimized+Manticore와 queue/reset smoke를 통과했지만 strict PASS라고 보고하지 않는다. manifest와 optimized archive를 v0.3.2로 갱신하기 전에는 toggle을 다시 실행하면 최종 모듈이 v0.2.6으로 되돌아갈 수 있다.

### 4.3 외부 검색엔진 대안 검증: Manticore 시험

이 절은 **Manticore 도입 지침이 아니라 현재 네이티브 MySQL 통합검색의 병목을 외부 인덱스로 분리할 수 있는지 검증한 기록**이다. 성능 시험을 빠르게 분리하기 위해 `ManticoreIntegratedSearch`가 PDO로 직접 읽었지만 G7에는 이미 `ScoutServiceProvider`의 커스텀 엔진 확장점이 있다. 따라서 별도 외부 검색 driver/registry를 신설할 필요는 없고, 향후 Manticore를 제품화한다면 기존 Laravel Scout `Engine`과 `core.search.engine_drivers` 훅을 사용해야 한다. 단, 현재 Scout를 우회하는 Repository 검색 연결과 색인 동기화 구현은 남는다. 이 차이는 이번 Manticore 읽기 성능·정확도 결과를 무효화하지 않지만 Scout 연동 완료 증거로 확대해서는 안 된다.

R 색인은 2.47초·최대 RSS 278,592KB, G 색인은 8.50초·최대 RSS 288,684KB였다. 유휴 searchd RSS는 데이터와 시점에 따라 약 55~105MB였다. 즉 검색 시 MySQL의 순간 900MB급 증가보다 예측 가능하지만 무료는 아니며, 색인 디스크와 동기화 프로세스 용량을 서버 사양에 포함해야 한다. 이번 검증은 plain index의 읽기 성능까지이며 신규·수정·삭제의 실시간 freshness는 완료 증거가 없다.

재색인은 반드시 서비스 계정으로 실행한다.

```bash
sudo -u manticore indexer --all --rotate
```

`sudo indexer --all --rotate`로 root 실행하면 `.new.*`가 root 소유가 되어 searchd rotation이 `Permission denied`로 실패할 수 있다. 연결 전환은 이 인덱스를 삭제하지 않고 G7의 driver만 바꾼다.

### 6.5 더미 데이터 생성·초기화 운영 증거

초기화는 웹 세션에서 대량 DELETE를 끝까지 기다리는 구조가 아니라 queue job으로 실행하고, 데이터셋 소유 범위를 20,000행 cursor 청크로 삭제한다. 게시판 후처리는 모든 댓글을 다시 세지 않고 board total·cache·고아 작성자 검색어만 정리한다.

| 삭제 대상 | 경과시간 | 프로세스 최대 RSS | swap | 결과 |
|---|---:|---:|---:|---|
| 게시글 100,000 + 댓글 125,204 + 회원 10,000 | 37.97초 | 별도 미확보 | 0 | 삭제 완료; 배포본 메서드 불일치 후 v0.3.2에서 0.30초 재개·최종화 |
| 게시글 200,000 + 댓글 250,692 + 회원 10,000 | 73.65초 | 107,340KB | 0 | 완료 |
| 게시글 400,000 + 댓글 501,041 + 회원 10,000 | 161.60초 | 107,456KB | 0 | 완료 |
| 상품 10,000 | 3.76초 | 안전 guard 통과 | 0 | 완료 |
| 상품 10,000 | 2.48초 | 안전 guard 통과 | 0 | 완료 |

세 게시판 작업의 합계는 273.22초지만 단일 “100만 건 삭제” 결과로 표현하지 않는다. 초기화 후 clean DB는 회원 1·게시글 5·댓글 14·상품/주문 0이었고, 고아 `board_post_author_terms`는 29,823→0, 게시판 합계도 원본과 일치했다.

몇 시간 멈춘 것처럼 보였던 운영 원인도 별도로 확인했다. dispatch는 `BENCHMARK_QUEUE_CONNECTION=database`, 실제 worker는 `queue:work redis`라 작업을 소비하지 못했다. 시험 VM은 benchmark connection을 `redis`, queue를 `default`로 통일하고 `config:cache` 후 worker를 재시작했다. 최종 runtime smoke에서 `config-cache queue 일치`, `첫 reset 준비`, `중복 준비 차단`, `Redis worker 완료`, `완료 job 재전달 멱등성`, `dispatch 실패 보상` 6개 검사가 모두 PASS였다. 작업 상세에는 대상 게시판명·slug·ID·예상 삭제량과 명시적 확인을 표시하고, 화면 전체가 깜빡이지 않도록 5초 순차 polling과 중단·재개 상태를 사용한다.

실제 `g7-bench.local` 관리자 화면에서도 G 게시판 작업의 대상이 `자유게시판 (freebd, ID 1) 100,000건`, `갤러리 (gallery, ID 2) 60,000건`, `40만건 (test40, ID 3) 40,000건`으로 표시되는지 확인했다. 초기화 확인창은 게시글 200,000·댓글 348,700·더미회원 100,000을 다시 명시했고, 취소 시 작업과 데이터가 그대로 유지됐다. 일반 쇼핑몰 생성 작업이 초기화 상태로 오인되던 응답도 수정했으며, 5초 polling 중 상세 제목 유지와 브라우저 경고·오류 0건을 확인했다.

최종 smoke 뒤 G 데이터는 회원 100,001·게시글 200,005·댓글 348,714·상품 20,000으로 그대로였고 작업 11~13은 모두 `completed`, 비종결 작업과 Redis queue는 0이었다. Manticore 색인도 게시글 194,064·상품 18,980·페이지 6건을 유지했다.

## 7. 서버 사양과 카페24 500원 호스팅 판정

### 7.1 공식 요구사항과 실측 권장안을 분리한다

[그누보드7 시스템 요구사항](https://github.com/jiwonpapa/gnuboard7/blob/codex/7.0.5-performance-lab/docs/requirements.md)은 PHP 8.2+, MySQL 8.0+ 또는 MariaDB 10.3+, 최소 디스크 700MB·권장 2GB+를 명시하지만 CPU와 RAM 최소값은 명시하지 않는다. 아래 CPU/RAM은 공식 사양이 아니라 이 문서의 데이터와 구성으로 얻은 운영 판단이다.

| 구성 | 판정 | 근거와 용도 |
|---|---|---|
| 4 vCPU·2GB | 부적합 | 가용 메모리 379MB에서 자원 guard가 3초 만에 중단. MySQL FULLTEXT 한 번의 RSS 증가 약 903MB를 감당하지 못함 |
| 4 vCPU·4GB | 저부하 smoke 하한 후보 | 21개 경로를 0.2 RPS·20초·1회 실행해 최소 가용 메모리 2,391MB, swap 0. 검색·색인·큐 중첩과 steady는 미검증 |
| **4 vCPU·8GB** | **현재 권장** | R/G 15 RPS A/B, R/G/X 검색 A/B/C, Manticore 색인을 분리 실행. 유효 일반 phase 최소 가용 메모리 6,537MB, 전 phase swap 0. 동시 중첩·soak는 미검증 |
| 8 vCPU·16GB 또는 DB/검색 분리 | 성장 구간 권장 | 높은 동시성, 큐·배치·색인 동시 실행, 데이터 증가 시 격리와 여유 확보. 이 시험의 직접 A/B 수치는 아닌 용량 계획안 |

새 데이터의 저트래픽 사이트에서 Manticore·Redis·Reverb·상시 큐를 쓰지 않는다면 2 vCPU·4GB부터 시작할 수 있다. 다만 이번 시험은 2 vCPU를 검증하지 않았으므로 이는 관측 결과가 아닌 실무 시작점이며, p95·가용 메모리·swap·DB slow query를 보고 확장해야 한다.

### 7.2 카페24 500원형: 구동은 조건부 가능, 운영 권장은 불가

**판정은 상품별로 다르다.**

| 상품 | 결론 | 이유 |
|---|---|---|
| 카페24 **뉴아우토반 절약형 500원** | **기본 구동 확인 / 운영 비권장** | [G7 설치 가이드](https://github.com/jiwonpapa/gnuboard7/blob/codex/7.0.5-performance-lab/INSTALL.md)는 이 상품의 설치를 검증했고, [공식 사양](https://hosting.cafe24.com/?controller=new_product_page&page=newautobahn)은 PHP 8.2·8.4, MariaDB 10.x, SSH와 700MB SSD를 제공한다. 다만 700MB는 G7 공식 최소 디스크와 정확히 같아 캐시·로그·업로드·업데이트 staging 여유가 없고 CPU/RAM은 공유 자원이다. |
| 카페24 **홈페이지 호스팅 절약형 500원** | **설치 불가** | [공식 사양](https://hosting.cafe24.com/?controller=new_product_page&page=homepage)은 합산 300MB(웹 200MB+스트리밍 100MB)로 G7 최소 700MB보다 작다. |

#### PHP 256M/512M이어도 통합검색 판정이 바뀌지 않는 이유

카페24의 [웹호스팅 메모리 안내](https://help.cafe24.com/faq/web-hosting/introduce/setup-management/wordpress_plugin_theme_install_memory_limit_error)는 일반 기본값을 128M으로 설명하고 필요 시 256M 또는 512M 조정을 안내한다. 실제 상품·계정이 256M이고 512M까지 상향되더라도 아래처럼 PHP와 DB 메모리는 분리되므로 통합검색 판정은 같다. 카페24도 [공유호스팅에서 과도한 상향은 서비스 제한 사유가 될 수 있다](https://help.cafe24.com/faq/wordpress/managed-wordpress/connection-error/wp_fatal_error_post_editing_fix/)고 안내하므로 512M은 계정 전체 자원 보장이 아니다.

| 자원 | `memory_limit` 영향 | 이번 시험에서 확인한 위험 |
|---|---|---|
| PHP/Laravel 요청 | [PHP `memory_limit`](https://www.php.net/manual/en/ini.core.php#ini.memory-limit)은 요청 스크립트의 PHP 힙 상한이다. 256M→512M은 모델 hydration·응답 조립 여유만 늘린다. | ID-first와 현재 페이지 hydration으로 줄일 수 있으나, 동시 PHP 요청의 합산 메모리와 공유 계정 자원은 보장하지 않는다. |
| MySQL/MariaDB FULLTEXT | **PHP `memory_limit` 적용 대상이 아니다.** DB 서버 프로세스가 별도 메모리를 사용한다. | 광범위 exact count 한 번에 `mysqld` RSS가 약 903MB 늘었다. PHP를 512M으로 올려도 이 증가량은 막지 못한다. MySQL의 관련 상한은 별도 [`innodb_ft_result_cache_limit`](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_ft_result_cache_limit)이다. |
| 외부 검색엔진(Manticore 시험 사례) | 별도 검색 서비스이므로 PHP 상한과 무관하다. | 공유호스팅은 계정 내부 daemon 운영을 전제로 할 수 없다. 외부 서비스를 선택하면 기존 Scout custom engine 확장점으로 연결할 수 있지만 별도 실측이 필요하며 특정 엔진 도입을 전제하지 않는다. |

따라서 공유호스팅 판정은 **설치·기본 CRUD=조건부 YES, 공개 MySQL 통합검색=NO**로 분리한다. 안전한 선택지는 통합검색 UI와 `/api/search`를 함께 비활성화하거나 외부 관리형 검색으로 분리하는 것이다. 현재 코어는 `G7_INTEGRATED_SEARCH_DRIVER=mysql|manticore`만 제공하고 명시적 `disabled` 모드가 없으므로, 공유호스팅을 공식 지원하려면 `G7_INTEGRATED_SEARCH_ENABLED=false` 같은 fail-closed 기능과 라우트·UI 동시 차단을 추가해야 한다. 행 수만으로 안전 기준을 정할 수 없고 검색어 매칭률·동시성에 좌우되므로, 카페24 실계정 부하 시험 전에는 안전 게시글 수를 보장하지 않는다.

뉴아우토반에서 큐·소켓·서버 기능을 모두 쓰지 않는 최소 런타임 구성은 다음과 같다. 단, 아래 MySQL 드라이버는 설치 호환 기본값일 뿐 **통합검색 운영 권장값이 아니다**. 명시적 disabled 모드가 구현되기 전에는 검색 UI·API를 별도로 차단해야 한다.

```dotenv
QUEUE_CONNECTION=sync
BROADCAST_CONNECTION="null"
CACHE_STORE=file
SESSION_DRIVER=file
FILESYSTEM_DISK=local
SCOUT_DRIVER=mysql-fulltext
G7_INTEGRATED_SEARCH_DRIVER=mysql
MAIL_MAILER=log
```

설치 후 실제 드라이버 정본인 `storage/app/settings/drivers.json`도 `cache=file`, `session=file`, `queue=sync`, `storage=local`, `websocket_enabled=false`, `search_engine=mysql-fulltext`인지 확인해야 한다. 신설 기본값은 `config/settings/defaults.json:108-140`에 같은 공유호스팅형 구성이 들어 있다. `.env`만 바꾸고 관리자 설정 정본이 다른 상태를 남기면 안 된다.

카페24 공유 웹호스팅은 [cron을 지원하지 않고](https://help.cafe24.com/faq/web-hosting/introduce/setup-management/cron-service-supported-hosting/), [Composer 직접 실행과 서버·OPcache 설정 변경도 지원하지 않는다](https://help.cafe24.com/faq/web-hosting/introduce/setup-management/module_daemon_restrictions/). 따라서 bundled vendor와 사전 빌드 에셋을 사용하고, 사이트맵·미리보기 정리·업데이트 확인·게시판 통계·주문 자동취소·장바구니 정리·마일리지 적립/소멸 같은 예약 작업은 끄거나 SSH에서 수동 실행해야 한다. 실제 계정은 PHP 필수 확장, `exec/proc_open/shell_exec`, MariaDB 10.3+, rewrite와 쓰기 권한을 인스톨러 사전 점검으로 통과해야 한다.

또한 카페24는 MariaDB 10.x를 제공하고, G7의 `app/Search/Engines/DatabaseFulltextEngine.php:185-200,299-320`은 MariaDB에서 MySQL ngram parser를 사용하지 않는다. 기본 검색은 동작할 수 있지만 한글 검색 품질과 대량검색 성능을 MySQL 8 ngram 또는 전문 외부 검색 backend와 동급으로 주장할 수 없다.

절약형은 일일 트래픽 1.6GB를 소진하면 다음 초기화 전까지 차단될 수 있고, 공유 CPU/RAM 상한이 공개 보장되지 않는다. 결론적으로 **통합검색을 끈 설치·기본 CRUD·극저트래픽 사이트만 조건부 YES이고, MySQL 통합검색·실시간·비동기·정기 작업·대량 한글검색·쇼핑몰 자동화를 포함한 정상 운영은 NO**다. 설치 호환성은 저장소 문서로 확인됐지만 PHP 256M/512M별 peak, 카페24 DB FULLTEXT 상한·동시성, 외부 검색 연결을 실계정에서 측정하지 않았으므로 성능 증거 수준은 `UNVERIFIED`다.

아래 조건이 깨지면 평균 지연시간이 좋아져도 튜닝 성공으로 보지 않는다.

1. 권한 결과, 공개 상태, 삭제 상태, 게시판 범위가 기준선과 같아야 한다.
2. 검색 결과가 잘렸으면 `total_relation=gte`, `total_is_exact=false`, `search_truncated=true`를 숨기지 않아야 한다.
3. 외부 검색 backend가 정확 결과를 반환하면 `total_relation=eq`이고 MySQL hydration 순서는 backend ID 순서를 보존해야 한다.
4. 외부 backend 장애 fallback이 원래의 무제한 MySQL FULLTEXT를 다시 실행하면 안 된다.
5. 검색 429는 일반 500으로 변환하지 않아야 한다.
6. 게시판 전용 인덱스 강제는 기본 board·비검색·ID sort에만 적용해야 한다.
7. 상품 `sales` 정렬은 현재 ID-first 최적화 대상이 아니므로 기존 의미를 유지해야 한다.
8. resource cache는 요청 문맥을 넘어서 사용자·통화·locale 결과를 공유하면 안 된다.
9. category static lookup은 필요한 조상을 먼저 prime하고 long-lived worker에서 요청 간 잘못된 상태가 남지 않아야 한다.
10. OFF/ON 비교는 같은 서버·DB·경로·부하에서 해야 하며 phase 사이 앱 캐시를 재생성해야 한다.
11. 전환 실패 후 source/runtime/schema가 섞인 상태를 성공으로 보고하면 안 된다.
12. `restore`는 사전 스냅샷이 완전할 때만 실행하고, 실패하면 비교 산출물을 유효 결과로 남기면 안 된다.
13. benchmark dispatch connection·queue 이름은 실제 worker와 같아야 하며, 다르면 생성·초기화를 시작된 작업으로 표시하면 안 된다.
14. 대량 초기화는 job 소유 범위 밖의 게시글·댓글·회원·상품을 삭제하면 안 되고 중단 후 같은 cursor에서 재개돼야 한다.
15. Manticore 재색인은 `manticore` OS 계정으로 실행하고 `.new.*` 소유권과 rotate 성공을 확인해야 한다.

## 11. ROI 기준 다음 작업 순서

1. 네이티브 MySQL 통합검색의 광범위 exact count를 재설계하고, 정확하지 않은 결과는 `gte/search_truncated`로 UI까지 명확히 표시한다.
2. 주문 정합성용 소량 corpus와 dataset-owned 대량·재개형 생성기를 구현해 인기상품·매출·재고 경로를 검증한다.
3. ecommerce 인덱스를 benchmark 모듈에서 정식 ecommerce upgrade step으로 옮긴다.
4. 검증된 정확 RPS 하네스로 R 30분 steady·2시간 soak와 G peak/spike/breakpoint를 완료한다.
5. 위 항목 뒤에 인기상품 집계와 cursor pagination을 측정 기반으로 검토한다.

Manticore는 ROI 작업 목록의 강제 도입 항목이 아니다. 외부 검색엔진을 선택할 경우 G7이 이미 제공하는 Laravel Scout custom engine 확장점을 사용하며, 이번 시험 결과는 그 선택지의 대안 가능성만 보여준다.

### 11.1 P0 구현 계약

아래 항목은 “방향”이 아니라 구현 인수 기준이다. 완료 보고에는 코드·자동 테스트·같은 조건의 VPS 수치·원복 결과를 모두 붙인다.

#### 11.1.1 주문 데이터 생성기

- **표면:** 기존 `WorkloadType::Commerce`에 `GenerationStage::Orders`와 `total_orders`를 추가하고 `StoreGenerationJobRequest`, `GenerationJobService`, `CommerceGenerationService`, planner, UI, progress/reset에 평균 상품수, 회원/비회원 비율, 2년 시간분포, 상태·결제·배송 분포, 인기상품 skew, seed, batch/chunk를 명시한다. 상품 생성 뒤 주문 단계가 이어지도록 해 상품 소유권·초기화를 중복 구현하지 않으며 migration·API 문서·module CHANGELOG도 갱신한다.
- **정합성 corpus:** 먼저 1천~5천 건은 `OrderProcessingService::createFromTempOrder()`를 통해 생성해 주문·옵션·주소·결제·배송·재고·마일리지 규칙의 기준 corpus로 삼는다. 외부 PG 실결제는 호출하지 않고 test provider/무통장 상태만 사용한다.
- **대량 corpus:** 10만~50만 건은 dataset 전용 bulk projector로 chunk 처리하되 `ecommerce_orders`, `ecommerce_order_options`, `ecommerce_order_addresses`, `ecommerce_order_payments`, `ecommerce_order_shippings`의 FK와 금액 합계를 기준 corpus와 대조한다. 취소·환불 상태를 만들면 해당 option·결제·재고·마일리지 부산물도 함께 맞춘다.
- **소유권·재개:** benchmark 소유 mapping table에 `generation_job_id/entity_type/entity_id`를 기록하고 결정적 business key+seed로 중복을 막는다. chunk cursor와 checksum을 commit해 중단 후 같은 위치에서 재개하며 queue 중복 소비도 멱등이어야 한다.
- **초기화:** FK 역순으로 **mapping에 있는 행만** 삭제하고, 비더미 참조나 mapping 누락이 있으면 삭제를 거부해 작업을 `failed`로 남긴다. 기존 상품·회원·실주문과 전역 주문 테이블을 지우지 않는다.
- **완료 검사:** `CommerceOrderGeneratorTest.php`를 신설하고 `GenerationJobServiceTest.php`, `StoreGenerationJobRequestTest.php`, `CommerceDatasetResetServiceTest.php`를 확장한다. 주문합계=옵션+배송-할인, 결제금액·통화 snapshot, 주문당 옵션 수, 재고/마일리지 변화, 고아 FK 0, 생성→중단→재개→reset 후 원본 행 수 복원을 자동 검증한 뒤에만 인기상품·매출·재고·주문목록 POST 부하를 `VPS_PASS` 후보로 올린다.

P0 구현에서 공개 API·코어 검색 계약·확장 의존성이 바뀌면 저장소의 버전 동기화 규칙에 따라 `requires.g7_version`/확장 dependency와 CHANGELOG를 함께 올린다. PHP 테스트, API 문서 생성, Pint, 하네스 strict/smoke, 같은 스냅샷 A/B가 모두 통과해야 구현 완료다.

## 12. 재현·후속 구현용 AI 프롬프트

아래 블록은 저장소 위치와 서버 값을 바꿔 외부 작업 세션에 바로 전달할 수 있다. 이 문서의 변경 지도·불변조건·측정 계약을 정본으로 삼고, 줄 번호가 달라지면 심볼을 다시 찾는다.

```text
역할
- Laravel 12 / PHP 8.2+ / MySQL 8 기반 그누보드7 성능 엔지니어다. 외부 검색엔진은 코어 정답으로 강제하지 않고 교체 가능한 adapter로 다룬다.
- 결론, 영향, 남은 위험을 먼저 보고하고 소스·EXPLAIN ANALYZE·HTTP 의미·CPU/RSS/swap으로 증명한다.

입력
- 저장소: <REPOSITORY_ROOT>
- 공식 기준선: tag 7.0.5 / d5065f1bc9ebdc31a3e4e0d0c2e757138fd7423f
- 성능 코어 튜닝 ref: 3379ed93
- 운영 하네스·benchmark v0.3.2 ref: 81fece53; 코어 ref와 섞지 않는다.
- 시험 서버: <SSH_HOST>, 앱 경로 <APP_ROOT>, 실행 사용자 <APP_USER>
- 관련 없는 미커밋 변경을 보존한다. reset/checkout/무단 stash/전체 git add를 금지한다.

목표
1. 이 문서의 C/B/S/E/D/H 항목을 파일·심볼 기준으로 재탐색한다.
2. 공식 7.0.5와 튜닝을 같은 서버·DB·데이터·요청·부하로 비교한다.
3. 홈, 공통, 게시판 목록·상세·검색, 쇼핑 홈·목록·검색, 통합검색을 분리한다.
4. 지연시간과 host/PHP/MySQL/searchd CPU·RSS, available memory, swap, 장기 쿼리를 함께 기록한다.
5. ON/OFF와 native MySQL/reference external adapter/disabled 연결 전환 및 물리 restore가 가역적인지 확인한다.
6. 권한·공개범위·삭제범위·정렬·페이지네이션·검색 정확도 메타가 보존되는지 검증한다.

필수 검토
- 기준선과 튜닝의 SQL 수, 스캔 행, 전송량, hydration 수를 비교한다.
- 각 인덱스의 WHERE/ORDER BY 목적과 실제 선택 여부를 EXPLAIN ANALYZE로 확인한다.
- count와 page query가 같은 조건·권한 범위를 쓰는지 확인한다.
- exact는 total_relation=eq, 제한형은 gte/total_is_exact=false/search_truncated=true인지 확인한다.
- 외부 backend 결과는 현재 페이지 ID만 MySQL에서 권한·공개범위를 재검증해 hydrate하고 backend 검색 순서를 보존해야 한다.
- 외부 backend 장애가 무제한 MySQL FULLTEXT로 전이되지 않도록 회로차단·disabled·bounded fallback을 확인한다.
- 일반 목록은 검색 throttle 대상이 아니며 실제 검색만 10회/분·named lock 보호를 받아야 한다.
- 기본 게시판 ID 정렬에서만 전용 인덱스를 강제하고 상품 sales 정렬은 별도 검증한다.
- 요청 캐시가 사용자·locale·currency·long-lived worker 사이에 누수되지 않는지 확인한다.
- 활성 확장·템플릿·DB 버전이 같은 배포 소스를 가리키는지 확인한다.

시험 절차
1. 작업트리, 런타임 strict status, DB 행 수·인덱스 shape, 서비스, 메모리·swap, 장기 쿼리를 저장한다.
2. S 데이터로 설치·권한·CRUD·응답 계약 smoke를 수행한다.
3. R 데이터로 warm-up 5 RPS 5분, steady 15 RPS 30분, peak 30 RPS 15분을 실행한다.
4. G 데이터로 peak·spike·breakpoint를 실행해 최초 SLO/자원 붕괴점을 찾는다. 30% 게시판 비중에서는 33 RPS를 넘기지 않고, 더 높은 부하는 비중 조정 또는 rate-limit 전용 phase로 분리한다.
5. X 데이터는 광범위 FULLTEXT와 deep pagination 같은 파괴 시험에만 사용한다.
6. 일반 A/B와 검색 A/B/C는 섞지 않는다. 검색은 희소·보통·광범위·병리적 검색어를 분리한다.
7. 각 상태를 최소 3회 반복하고 HTTP·의미 오류·drop·sampler heartbeat를 함께 판정한다.
8. 종료 상태는 입력으로 지정한 검색엔진으로 확인한다. Manticore 비교 phase를 실행했다면 MySQL 전환은 연결만 바꾸고 서비스·인덱스는 보존한다.

안전장치
- available memory 400MiB 미만이 3회 연속이면 중단한다.
- phase 종료 후 최소 available memory가 전체의 25% 미만이면 실패 처리한다.
- swap이 시작 대비 64MiB 이상 증가하면 중단한다.
- HTTP/의미 오류·iteration drop·sampler heartbeat 단절이 있으면 해당 phase를 무효화한다.
- 5초 이상 DB query/transaction이 있으면 전환을 중단한다.
- FULLTEXT cap은 optimized에서 32MiB인지 확인하고 restore는 캡처한 원래 값만 복원한다.
- 대량 삭제와 OPTIMIZE/TABLE rebuild는 웹 요청 안에서 실행하지 않는다.
- benchmark queue connection/name이 실제 worker와 같은지 시작 전에 확인한다.
- Manticore 비교 phase에서만 full index를 `sudo -u manticore indexer --all --rotate`로 실행한다.
- 주문 더미는 도메인 Service/Helper를 거친 정합성 corpus와 dataset-owned 대량 생성기를 분리해 별도 DB 스냅샷에 생성한다.

판정과 산출물
- CODE_ONLY, AUTO_PASS, VPS_PASS를 구분한다.
- 오류·누락 결과를 빠른 성공으로 계산하지 않는다.
- 다른 서버·데이터·부하의 숫자를 같은 A/B로 합치지 않는다.
- 서버 권장치는 공식 요구사항과 관측치를 구분한다.
- Manticore 수치는 외부 검색엔진의 대안 가능성을 검증한 시험 결과로만 보고하고 특정 제품 도입 권고로 결론 내리지 않는다.
- G7에는 이미 Laravel Scout custom engine 확장점이 있으므로 별도 외부 검색 driver/registry 신설을 제안하지 않는다.
- 현재 네이티브 MySQL 통합검색의 exact count·메모리·결과 누락 문제를 핵심 결함으로 보고하고, Manticore는 대안성 시험 결과로만 제시한다.
- 변경별 파일:라인, 심볼, 이전 병목, 새 알고리즘, 인덱스·실행계획, 테스트, 실측, rollback, 남은 위험을 기록한다.
- 일반 A/B, 검색 A/B/C, 정확도 메타, 자원 사용량, 실패·미완료 항목을 결과에 직접 포함한다.
```
