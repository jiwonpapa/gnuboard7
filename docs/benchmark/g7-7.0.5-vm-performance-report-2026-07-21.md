# 그누보드7 7.0.5 VM 성능·검색·서버 사양 분석

> **대체된 초기 조사 문서:** 이 문서의 “Manticore 즉시 채택”, “4GB 실측 운영 하한” 결론은 후속 R/G 운영부하와 증거 경계 검토로 대체됐다. 외부 공개와 현재 판단에는 [최신 상세 보고서](https://github.com/jiwonpapa/gnuboard7/blob/codex/7.0.5-performance-lab/docs/benchmark/g7-7.0.5-performance-tuning-code-map-and-implementation-prompt-2026-07-21.md)와 [게시판 공개용 코드 지도](https://github.com/jiwonpapa/gnuboard7/blob/codex/7.0.5-performance-lab/docs/benchmark/g7-7.0.5-performance-tuning-code-map-board-post-2026-07-21.md)를 사용한다.

- 작성일: 2026-07-21 KST
- 기준 버전: 공식 태그 `7.0.5` (`d5065f1b`)
- 최종 튜닝 커밋: `3379ed93`
- 시험 서버: `https://192.168.0.141` (`g7-bench.local` VM)
- 최종 상태: 튜닝 ON, Manticore 연결 ON, 4 vCPU·8GB RAM·2GB swap

## 결론

1. **그누보드7 코어·게시판·쇼핑몰 튜닝은 유지할 가치가 충분합니다.** 동일 VM·동일 DB·동일 21개 경로에서 평균 호스트 CPU는 34.0%, MySQL CPU는 59.3% 감소했고 모든 응답 검증과 스케줄 검증을 통과했습니다.
2. **게시글 70만 건급 통합검색에는 Manticore 도입이 맞습니다.** 튜닝 MySQL 통합검색은 1.815초에 일부 결과만 반환했지만 Manticore는 0.112초에 게시글 678,866건을 정확히 반환했습니다. API 기준 16.3배, 지연시간 93.85% 개선입니다.
3. **다만 현재 Manticore 연결 범위는 통합검색입니다.** 일반 게시판 내부검색은 아직 MySQL 제한형 fallback이라 실제 97,017건 중 42건 하한만 표시합니다. 다음 최우선 작업은 게시판 직접검색을 같은 검색 서비스에 연결하는 것입니다.
4. **이 데이터 규모의 권장 실서버는 4 vCPU·8GB입니다.** 4 vCPU·4GB는 운영 가능한 실측 하한이고, 2GB는 단일 요청은 처리해도 가용 메모리가 379MB까지 내려가 fail-closed 되어 실운영 사양으로 부적합합니다.
5. **일반 공유호스팅은 소규모·기능 축소형만 가능합니다.** 현재 데이터와 Redis·큐·Reverb·Manticore를 모두 쓰는 구성은 VPS/VM이 필요합니다.
6. **Rust 전면 재작성 ROI는 낮습니다.** 확인된 병목은 PHP 실행 자체보다 MySQL FULLTEXT, 잘못 선택된 인덱스, 과도한 count/정렬, 삭제 후 InnoDB 공간 미회수입니다. Rust로 바꿔도 이 병목은 그대로 남습니다.

## 2. 측정 방법

- 일반 경로: 홈, 홈 구성 API, 게시판 목록·상세·이전다음, 쇼핑 홈·목록·상세·검색 등 21개 경로.
- 일반 A/B: 공식 7.0.5 동작과 튜닝 동작을 같은 VM에서 각각 3회 반복했습니다.
- 검색 A/B/C: `공식 7.0.5 + MySQL`, `튜닝 + MySQL`, `튜닝 + Manticore`를 통합·게시판·상품 검색별 3회 측정했습니다.
- 자원: `/proc`, 프로세스 RSS, load average를 1초 간격으로 수집했습니다. CPU 값은 4코어 전체 호스트 용량 대비 비율입니다.
- 안전장치: HTTP 오류, 의미 검증 실패, iteration drop, 메모리 400MB 미만 3회, swap 64MB 증가 시 실패 처리합니다.
- 비교 원칙: 동일 서버, 동일 데이터, 동일 요청, 전환 전후 캐시 재구축, 최종 상태 자동 복구입니다.

일반 A/B는 낮은 고정 부하에서 회귀와 경로별 비용을 비교한 시험입니다. 최대 동시접속 처리량 시험은 아니므로 이 결과만으로 최대 TPS를 주장하지 않습니다.

## 4. 검색 A/B/C와 메모리 고갈 원인

검색어는 통합·게시판 `운영`, 상품 `노트북 파우치`입니다.

| 상태 | 검색 | 중앙값 | 결과 | 정확성 |
|---|---|---:|---:|---|
| 공식 + MySQL | 통합 | 98ms | 페이지 2건만 표시 | 게시글 누락, 실패 |
| 공식 + MySQL | 게시판 | 55ms | HTTP 500 | MySQL error 188 |
| 공식 + MySQL | 상품 | 111ms | 1,878 | 정확 |
| 튜닝 + MySQL | 통합 | 1,815ms | 8 | 제한형 하한, 불완전 |
| 튜닝 + MySQL | 게시판 | 144ms | 42 | 제한형 하한, 불완전 |
| 튜닝 + MySQL | 상품 | 113ms | 1,878 | 정확 |
| 튜닝 + Manticore | 통합 | **112ms** | **678,868** | **정확** |
| 튜닝 + Manticore | 게시판 | 85ms | 42 | 아직 MySQL 경로, 불완전 |
| 튜닝 + Manticore | 상품 | 86ms | 1,878 | 현재 MySQL 경로, 정확 |

Manticore 통합검색의 게시글은 678,866건이며 `total_relation=eq`, `search_truncated=false`가 현재 실응답에서 확인됐습니다. 기존 검색 비교 파일의 `search_truncated=true` 한 필드는 당시 하네스의 boolean fallback 파서 오류이며, 응답 완전성 판정과 건수에는 영향을 주지 않았습니다. 파서는 이후 수정했습니다.

### 검색 중 서버 자원

| 상태 | 호스트 CPU 평균/최대 | 최소 가용 메모리 | MySQL RSS 처음→최대 | searchd RSS 처음→최대 | swap |
|---|---:|---:|---:|---:|---:|
| 공식 + MySQL | 4.690/18.225% | 6,658MB | 543→587MB | 90→90MB | 0MB |
| 튜닝 + MySQL | 14.640/27.628% | 6,358MB | 585→877MB | 90→90MB | 0MB |
| 튜닝 + Manticore | 6.544/23.171% | 6,510MB | 592→667MB | 89→103MB | 0MB |

Manticore는 튜닝 MySQL 대비 평균 호스트 CPU를 55.3% 줄였습니다. MySQL RSS 증가는 약 291MB에서 76MB로 줄었고, searchd 증가는 약 13MB였습니다.

### 2GB FULLTEXT 캐시가 메모리를 채운 이유

원래 `innodb_ft_result_cache_limit=2GB` 상태에서 동일한 광범위 MySQL FULLTEXT count를 1회 실행하면:

- 결과: 678,866건
- 소요: 4.898초
- mysqld RSS: 511MB → 1,414MB, **약 +903MB**
- 시스템 가용 메모리: 약 **-905MB**

즉, 사용자가 본 “검색 한 번에 2GB 서버 메모리 풀” 현상은 재현됐습니다. 32MB 안전 상한에서는 메모리 폭증 대신 MySQL error 188이 발생하므로, MySQL만으로는 `정확한 광범위 검색`과 `낮은 메모리`를 동시에 만족시키기 어렵습니다.

Manticore 직접 count는 같은 678,866건을 약 23ms에 반환했습니다. 직접 쿼리 기준 약 213배, 실제 통합검색 API 기준 16.3배 빠릅니다. 현재 MySQL FULLTEXT 결과 캐시 상한은 32MB로 영구 설정했습니다.

## 5. Manticore 도입 판단

### 도입 결론

- **통합검색: 즉시 채택** — 성능, 정확성, 메모리 모두 압도적으로 개선됩니다.
- **일반 게시판검색: 다음 최우선 연결** — 현재 42건 하한이지만 Manticore의 동일 게시판 정확 건수는 97,017건입니다.
- **쇼핑몰검색: 현 시점 선택 사항** — 상품 2만 건에서는 MySQL이 정확하고 86~113ms이므로 ROI가 낮습니다. 상품 수가 크게 늘거나 복합검색이 무거워질 때 연결합니다.

### 운영 전 남은 조건

현재 인덱스는 재현 가능한 정적 benchmark용 plain index입니다. 실서비스 도입 전에는 다음 중 하나가 필요합니다.

1. 게시글·상품 생성/수정/삭제 이벤트로 delta/RT 인덱스를 갱신하거나,
2. 짧은 주기의 delta index + 주기적인 full rebuild를 운영하거나,
3. Laravel Scout write path를 Manticore RT table에 연결합니다.

이 동기화가 없으면 검색 성능은 좋아도 새 글과 삭제 글의 freshness가 보장되지 않습니다. 따라서 현재 상태는 **검색 성능·장애 fallback 검증 완료**, **실시간 인덱스 동기화는 미완료**입니다.

## 7. 2GB·4GB·8GB 사양 판단

G7 공식 요구사항 문서에는 PHP 8.2+, MySQL 8.0+/MariaDB 10.3+, 디스크 700MB, PHP `memory_limit` 128MB 같은 설치 요구사항은 있지만 서버 전체 CPU·RAM 최소치는 명시되어 있지 않습니다. 아래는 공식 최소사양이 아니라 이번 70만 게시글 데이터의 **실측 권장치**입니다.

| VM | 결과 | 최소 가용 메모리 | swap | 판단 |
|---|---|---:|---:|---|
| 4 vCPU·2GB | 3초 만에 메모리 안전장치 중단 | 379MB | 0MB | 실운영 불가 |
| 4 vCPU·4GB | 21개 경로 정상, 오류·drop 없음 | 2,391MB | 0MB | 실측 운영 하한 |
| 4 vCPU·8GB | 일반·검색·인덱싱 모두 정상 | 4,520MB 이상 | 0MB | 권장 |

### 권장안

- 소규모·저트래픽·Manticore 없음: 2 vCPU·4GB부터 검토 가능.
- 이번과 같은 70만 게시글·87만 댓글·2만 상품: **4 vCPU·8GB 권장**.
- full reindex, 대량 더미 생성/삭제, 백업을 피크 트래픽과 겹치지 않게 운영하면 8GB로 충분합니다.
- 동시접속이 크거나 인덱싱·백업을 상시 병행하면 8 vCPU·16GB 또는 DB/검색 분리를 검토합니다.
- 4GB에서 indexer 최대 313MB와 MySQL 순간 증가가 겹치면 여유가 줄므로, full reindex는 비피크 시간에 실행해야 합니다.

## 8. 일반 공유호스팅 가능 여부

공식 문서는 공유호스팅 설치 자체는 가능하다고 설명하지만 Supervisor, cron 간격, PHP 확장, Redis, 커스텀 포트, 파일 권한 제한을 명시합니다. 이번 구성은 다음 이유로 일반 공유호스팅에 맞지 않습니다.

- Manticore 설치·서비스 관리와 9306 포트가 필요합니다.
- 큐 워커, 스케줄러, Reverb를 상시 관리해야 합니다.
- MySQL 설정과 인덱스를 제어해야 합니다.
- 대량 삭제 후 테이블 재구성, 백업, 인덱싱에 충분한 임시 디스크가 필요합니다.
- 호스팅 사업자의 CPU throttling과 쿼리 제한을 직접 관찰·조정할 수 없습니다.

결론적으로 작은 커뮤니티를 큐 동기 처리·외부 WebSocket·MySQL 검색으로 축소하면 공유호스팅도 가능하지만, 현재 데이터와 전체 기능은 VPS/VM이 맞습니다.

## 9. 100만 건 삭제가 끝났는데 DB가 큰 이유

논리 행 수를 비교하면 100만 건 삭제는 반영됐습니다. 문제는 InnoDB가 삭제된 페이지를 테이블 내부 free space로 남기고 파일을 운영체제에 즉시 반환하지 않는다는 점입니다.

- 원본 시험 DB: 약 3,509.5MB
- 같은 논리 데이터를 fresh restore한 VM: 568.1MB
- 차이: 약 2.94GB, 6.2배

따라서 다시 삭제할 문제가 아니라, 유지보수 시간에 `OPTIMIZE TABLE` 또는 table rebuild를 해야 합니다. 이 작업은 잠금·I/O·임시 디스크를 많이 쓰므로 웹 요청이나 100만 건 reset 요청 안에서 실행하면 안 됩니다. 사전 백업, 필요한 추가 디스크 확인, 비동기 작업, 진행률과 취소·재개 상태가 필요합니다.

## 11. 하네스와 원상복구 방식

### 일반 튜닝 OFF/ON

```bash
scripts/benchmark/g7-performance-toggle.sh off \
  --scope all --host 192.168.0.141 \
  --root /home/g7bench/public_html --app-user g7bench \
  --db g7bench --base-url https://192.168.0.141

scripts/benchmark/g7-performance-toggle.sh on \
  --scope all --host 192.168.0.141 \
  --root /home/g7bench/public_html --app-user g7bench \
  --db g7bench --base-url https://192.168.0.141 \
  --optimized-ref 3379ed93
```

`off`는 공식 7.0.5 동작을 선택하고 튜닝 인덱스를 invisible 처리합니다. Manticore 패키지·서비스·설정·인덱스는 삭제하지 않습니다.

### 검색 연결만 MySQL/Manticore로 전환

```bash
scripts/benchmark/g7-search-backend-toggle.sh mysql
scripts/benchmark/g7-search-backend-toggle.sh manticore
scripts/benchmark/g7-search-backend-toggle.sh status
```

`mysql`은 G7의 연결 설정만 되돌립니다. Manticore는 그대로 설치·실행되고 인덱스도 유지됩니다.

### 자동 A/B

```bash
G7_PERF_HOST=192.168.0.141 \
G7_PERF_ROOT=/home/g7bench/public_html \
G7_PERF_APP_USER=g7bench \
G7_PERF_DB_NAME=g7bench \
G7_PERF_BASE_URL=https://192.168.0.141 \
scripts/benchmark/g7-ab-benchmark.sh --repeats 3

scripts/benchmark/g7-search-ab-benchmark.sh --repeats 3
```

두 하네스는 오류·중단 시에도 최종적으로 튜닝 ON을 복구합니다. 검색 A/B/C 하네스는 최종 상태를 튜닝 ON + Manticore 연결 ON으로 복구하며 Manticore를 제거하지 않습니다.
